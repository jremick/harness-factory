# Compatibility

This document freezes the beta candidate's local compatibility contract. It
does not announce or publish a beta release. The release page and package
metadata remain authoritative for any future published version.

## Supported versions and targets

| Surface | Supported value |
| --- | --- |
| Factory package in this source snapshot | `0.2.0a1` |
| CLI JSON response contract | `0.1.0` |
| Python | `3.12` |
| Host platforms in CI | Ubuntu and macOS |
| HDP definition | Draft `0.1.0`, schema `urn:hdp:schema:0.1.0` |
| HIR | `0.1.0` |
| Codex target binding | `bindingVersion: 0.1.0` |
| Codex adapter | `adapterVersion: 0.1.0` |
| Generated harness manifest | `manifestVersion: 1` |
| Installer ownership manifest | `manifestVersion: 1` |
| Installer recovery journal | `schemaVersion: 1` |
| Release manifest and evidence | `0.1.0` |
| Complete target adapters | Codex only |

The implementation currently uses exact version markers for these surfaces.
`0.1.x` or another target is not a compatibility promise. Unknown or
unsupported values fail closed; they are not silently coerced or upgraded.

The canonical schema and the analyser skill copy are pinned byte-for-byte to
SHA-256 `4cb4a85dcdfe6b176be5760a1f109c720a66ea80a6179f94928e3683f1566e96`.
The Factory validation suite includes the checked-in reference examples, but
adapter support remains limited to the target-neutral `software-development`
profile through the Codex binding.

## Accepted alpha inputs and artifacts

The beta candidate accepts the alpha's convention-driven project layouts:

- `harness/hdp.yaml` or `harness/hdp.json` with
  `harness/bindings/codex.yaml` or `harness/bindings/codex.json`;
- the legacy root layout `hdp.yaml` or `hdp.json` with
  `bindings/codex.yaml` or `bindings/codex.json`;
- a beta generated harness containing a version-`1` `.hdp/manifest.json`,
  regular manifest-owned files and matching SHA-256 digests, with explicit
  `0.1.0` HIR/source-HDP, Codex binding and adapter markers;
- the exact released alpha generated format from Factory `0.2.0a1` (no
  binding/adapter runtime markers), when every generated byte matches the
  canonical alpha renderer; and
- an existing installer ownership manifest with `manifestVersion: 1`.

An interrupted install may leave a version-`1` recovery journal. It is a
recovery record, not a normal input: later commands stop with the same generic
unfinished-installation conflict in dry-run and live mode, return exit `2`
with the marked conflict JSON when requested, and never parse or replay an
arbitrary journal supplied by a target checkout. The generic conflict is
intentional; it avoids turning hostile journal contents into diagnostics.

Strict audit distinguishes a standalone generated root from an installed
repository. A standalone root must contain only its manifest-owned generated
files. An installed repository must contain a valid ownership manifest that
matches the generated manifest and enumerates every generated file and digest;
only the exact installer control files (`.harness-factory/install-manifest.json`
and, when present, `.harness-factory/install.lock`) are outside that ownership
set. Unrelated repository files are not treated as generated or included in
the installed harness digest.

Dependency directories excluded from analysis, including `node_modules` and
`.venv`, may contain symlinks without invalidating an installed harness. These
entries are not inspected or included in its subject digest. Generated files,
their parent paths and installer controls still reject symlinks or tampering.
Standalone generated bundles and release payloads retain their closed-tree
checks; the installed-repository exception does not apply to them.

The checked-in [alpha compatibility fixtures](../tests/fixtures/compatibility/README.md)
include immutable source/layout bytes and a digest-pinned alpha generated
bundle. Tests consume the generated bundle directly through install, strict
audit, package and release verification without regenerating it under current
code. They are deterministic format fixtures, not evidence of broad target or
behavioural compatibility.

The `hdp` executable remains available for the alpha low-level command names.
The `generate` and `inspect` aliases remain hidden and are compatibility
aliases for `compile` and `analyse`. Import-level compatibility for third-party
Python callers is not promised.

## Unsupported inputs and diagnostics

The beta candidate does not provide an implicit migration or a general
cross-version reader. These inputs fail closed:

- an HDP definition whose `hdpVersion` is not `0.1.0`;
- a Codex binding whose `bindingVersion`, `adapterVersion` or target is not
  supported;
- a generated harness, installer manifest or installer journal with an
  unsupported version marker; and
- a release manifest or evidence object outside the exact supported format.

Version failures identify the observed and supported values (including whether
the value is numeric or a string) and say:
“No automatic migration is provided; update the source explicitly and rerun
validation.” Structural, semantic, conflict and eligibility failures retain
the documented exit classes in the [CLI reference](cli.md). Parse, missing
input and other operational failures report an error on stderr and emit no
machine-readable stdout.

The [negative compatibility fixtures](../tests/fixtures/compatibility/) cover
unsupported HDP and binding versions. They intentionally stop before any
generation or installation write, so a failed compatibility check cannot
partially migrate a project.

## Recovery and rollback

There is no automatic rollback across a version migration because no implicit
migration exists. For an installer interruption, the existing version-`1`
`install-transaction.json` journal remains the recovery point: subsequent
operations stop with the generic unfinished-installation conflict, the target
is inspected, and explicit manual recovery is required before retrying. The
pre-existing journal is kept opaque and is never parsed or replayed by normal
install; this is the rollback safety boundary. Generated output and release
payloads remain digest-bound; an unsupported artifact must be retained for
inspection or restored from the caller's version-controlled source, not
rewritten in place by the beta CLI.

The package's factory version and the HDP/HIR, binding, manifest, evidence and
CLI response versions evolve independently. A future migration must be an
explicit deterministic command or documented transformation with old/new
digests, source maps where applicable, fixtures, and rollback tests.
