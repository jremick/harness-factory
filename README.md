# Harness Factory

[![CI](https://github.com/jremick/harness-factory/actions/workflows/ci.yml/badge.svg)](https://github.com/jremick/harness-factory/actions/workflows/ci.yml)

> [!IMPORTANT]
> **Alpha release — [`v0.2.0a1`](https://github.com/jremick/harness-factory/releases/tag/v0.2.0a1).**
> You can try the main workflow today, but commands and file formats may change
> before the first stable release. It is not ready to be treated as a production
> security control.

Harness Factory is a tool for setting up an AI coding assistant in a consistent,
reviewable way.

You write down what the assistant should do, which tools and files it may use,
what it must not do, and how its work should be checked. Harness Factory checks
that description and creates the files Codex needs, such as `AGENTS.md`, an
Agent Skill and project settings. It can then place those files into a code
repository without silently replacing files it does not own.

The shared format used to describe those rules is called a Harness Definition
Package, or HDP. Its separate, tool-independent specification lives in the
[`hdp-reference` repository](https://github.com/jremick/hdp-reference). This
repository is the working tool that reads an HDP and builds a Codex setup from
it.

## Why use it?

- **Write the rules once.** Generate the different files Codex needs instead of
  copying the same instructions by hand.
- **Make changes easier to review.** Preview every installed file and keep a
  record of where generated content came from.
- **Get repeatable results.** The same reviewed input produces the same files
  and checksums.
- **Keep unknowns visible.** When inspecting an existing setup, the analyser
  reports what it found, what it inferred and what it could not determine.

## How it works

1. **Describe** the job, limits and checks in a small harness project.
2. **Build** the Codex files and check the description for mistakes.
3. **Review and install** the generated files into a target repository.
4. **Verify or audit** the result before relying on it.

Harness Factory prepares and checks the assistant's setup. Codex still runs the
work, and the operating system or runtime must enforce real security boundaries.

## Five-minute start

Prerequisites: Python 3.12 and [`uv`](https://docs.astral.sh/uv/).

```bash
uv tool install \
  https://github.com/jremick/harness-factory/releases/download/v0.2.0a1/harness_factory-0.2.0a1-py3-none-any.whl

harness doctor
harness init my-harness --template codex-sdlc
harness build my-harness
harness install /path/to/your-repository --project my-harness --dry-run
harness install /path/to/your-repository --project my-harness
```

Review `my-harness/harness/hdp.yaml` before installation. The bundled template is
a conservative software-development example, not an authorization policy for
every repository. `--dry-run` reports every managed file and refuses to replace
unowned or locally modified files.

The main workflow has seven commands:

```text
harness init      create a project from a starter or empty HDP
harness build     validate, normalize and compile it
harness install   safely copy manifest-owned files into a repository
harness audit     reconstruct an evidenced draft HDP from an existing harness
harness verify    rebuild and run deterministic static conformance
harness release   require bound evidence, package and verify an eligible release
harness doctor    report local prerequisites without reading credentials
```

The lower-level `hdp` command remains available for schema, compiler, analyser
and package-development workflows. See the [CLI reference](docs/cli.md).

## Audit an existing harness

```bash
harness audit /path/to/repository --output analysis
```

The analyser records findings as `observed`, `declared`, `inferred` or `unknown`
with provenance, confidence and conflicts. A partial or invalid reconstruction
is reported honestly and exits non-zero unless `--allow-partial` is explicit;
it is never silently made generation-ready. Exact round-trip parity is supported
for harnesses generated by this factory. Foreign-harness reconstruction remains
an experimental draft surface and has not passed the held-out zero-false-
assertion promotion gate. The same
workflow is available as the
[`analyse-existing-harness` Agent Skill](skills/analyse-existing-harness/SKILL.md).

## What is enforced

- JSON Schema 2020-12, semantic validation and target-neutral HIR invariants
- deterministic Codex rendering, artifact digests and source maps
- secret, unsafe-capability and generated-skill structural checks
- content-bound verification evidence and post-package tamper detection
- explicit Codex sandbox probes during live behavioural evaluations, with
  failures retained and release eligibility denied

Generated `scripts/harnessctl.py` is an allowlisted command recorder and
precheck. It is not an OS sandbox. Filesystem, process, network and resource
boundaries must be enforced by the target runtime.

## Status and scope

This repository is at **Stage 2 — Public Alpha**. The Codex adapter is the only
complete target adapter. The checked-in task corpus covers one feature, defect
fix, constrained refactor and policy-block case. Live results are evidence for
those exact subjects and runs, not a general software-engineering success rate.

See the current [verification report](docs/verification-report.md),
[limitations](docs/limitations-backlog.md) and
[stable-release checkpoint plan](docs/stable-release-checkpoint.md).

The provider-neutral HDP specification and versioned reference snapshot live in
[`jremick/hdp-reference`](https://github.com/jremick/hdp-reference). This
repository is the non-normative factory implementation.
